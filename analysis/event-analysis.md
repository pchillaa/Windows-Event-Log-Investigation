## 1. Исходные данные

Журнал содержит 4 события произошедших за примерно 4 секунды (09.09.2020 16:18:23 -> 16:18:27). Все события относятся к аутентификации Windows (Logon).

## 2. Разбор событий

Начнём с первого снизу так как оно произошло раньше всего по хронологии и дальше будем двигаться вверх по списку. Для понятности подпишем каждое событие в соответствии с их порядковым номером, автоматически генерируемым Windows для событий во вкладке Подробности - Режим XML - Поле <EventRecordID>. Исходные данные с подписанными событиями можно посмотреть на скриншоте [../screenshots/initial_data.png].

Примечание: Идентификация по Record ID при импорте/экспорте файла .evtx может отличаться, потому такой вид обозначений используется только для удобства в данном конкретном разборе.

### 2.1 Событие 137222 (16:18:23)

Все поля показаны на скриншоте [../screenshots/event_137222.png]

Поля на которые стоит обратить внимание в первую очередь:

- SubjectUserName: IEUser

Имя субъекта, инициализировавшего действие.

- SubjectDomainName: MSEDGEWIN10

Имя домена (или компьютера) учетной записи, которая инициировала действие

- LogonType 2

Интерактивный вход

- LogonProcessName Chrome
- ProcessName C:\Program Files (x86)\Google\Chrome\Application\chrome.exe

Здесь становится интереснее. Почему браузер инициирует вход? Кто-то пытается пытается подключиться к машине эксплуатируя браузер? Процесс выглядит легитимным, но нужно учитывать что мы не знаем полного контекста в котором были записаны события. Возможно, что сам файл браузера был изменён злоумышленником. Если это действительно так, то запрос должен поступать с неочевидного адреса. Чтобы убедиться, посмотрим что происходит по сети.

- IpAddress (Пусто)
- IpPort (Пусто)
	
Теория с атакой по сети отпадает, так как запрос на вход совершается браузером локально. Смотрим дальше.

- Status 0xc000006d

Ошибка аутентификации

- SubStatus 0xc000006a

Введён неверный пароль или опечатка при вводе пароля

По одному событию пока трудно сказать что именно происходит. Зачем браузеру производить интерактивный вход локально? Нам нужно больше контекста, поэтому переходим к следующему событию

### 2.2 Событие 137223 (16:18:25)

Подробности в скриншоте [../screenshots/event_137223.png]
Смотрим что происходит на этот раз.

- TargetUserName SYSTEM
- TargetDomainName NT AUTHORITY

Попытка повышения привилегий?

- LogonType 5

Запуск службы, не интерактивный вход человека. Здесь происходит что-то автоматическое.

- LogonProcessName Advapi
- ProcessName C:\Windows\System32\services.exe

Теперь мы поняли что это запуск менеджера управления службами. Он всегда вызывает LogonType 5. Это нормальная системная активность и не является взломом. Но в связи с чем понадобился её вызов?

Так же появились новые поля - ImpersonationLevel, RеstrictedAdminMode, TargetOutboundUserName, TargetOutboundDomainName, VirtualAccount, TargetLinkedLogonId и ElevatedToken. Просмотрев их можно сделать следующие выводы:

ImpersonationLevel = %%1833 (Impersonation) - стандарт для локальных процессов. Опасности нет. TargetOutboundUserName и TargetOutboundDomainName пусты. Сетевого взаимодействия нет. В остальных параметрах всё тоже в пределах нормы: RestrictedAdminMode = - (не RDP-вход), VirtualAccount = %%1843 = No (не виртуальная учётная запись), TargetLinkedLogonId = 0x0 (связи нет, самостоятельный вход службы), ElevatedToken = %%1842 = Yes (полный токен, ожидаемо для SYSTEM). Наблюдаем дальше.

### 2.3 Событие 137224 (16:18:27)

[../screenshots/event_137224.png]

Здесь мы видим похожий набор полей как в событии 137222 когда у нас была провальная попытка входа в систему от процесса chrome.exe. Только на этот раз появляется значение в TargetLinkedLogonId - 0x1cd964 и попытка входа успешная. Это означает что событие указывает на существование связанного токена 0x1CD964, который, вероятно, появится в следующем событии.

Мы уже знаем что это автоматический процесс запущенный chrome.exe для которого понадобились системные сервисы и сетевого взаимодействия нет. Поведение меньше становится похоже на атаку и больше на запрос Chrome прав доступа для осуществления своих функций. Это гипотеза, которую мы проверим в дальнейшем.

Запомним TargetLogonId этого события - 0x1cd8f6. По логике, TargetLogonId последнего события будет 0x1cd964, если они действительно соединены.

### 2.4 Событие 137225 (16:18:27)

[../screenshots/event_137225.png]

По сути происходит одновременно с предыдущим. Разница между 137224 и 137225 — 145 микросекунд, что несовместимо с действиями человека. Видим TargetLogonId - 0x1CD964, событие определенно точно связано с тем что мы рассматривали ранее и TargetLinkedLogonId - 0x1CD8F6 это подтверждает. Это признак пары токенов, созданных в рамках одной операции. При двух независимых входах (например, при повторной аутентификации атакующего) ссылок не было бы — каждая сессия
существовала бы сама по себе.

Отличается значение ElevatedToken - в данном событии это токен без повышенных привилегий. Тоже возьмём на заметку.

### 2.5 Заключение по событиям

Из изученных ранее событий самым вероятным выводом будет то, что Chrome запрашивает права у операционной системы на выполнение своих функций. Это будет являться кратким заключением, можно остановаться и на этом. Но можно и задаться вопросом - для чего ему это? Чтобы дать ответ нужно понимать как работает сам браузер.

Chrome использует многопроцессную архитектуру для безопасности: каждая вкладка и плагин работают в отдельном процессе с ограниченными правами (sandbox) . Чтобы создать такой процесс, Chrome должен получить у операционной системы токен доступа с урезанными привилегиями. Именно этот запрос токена Windows и записывает в Security Log как событие 4624 (или 4625 при неудаче). Самое сильное доказательство — это события 137224 и 137225. Они не просто идут подряд, они ссылаются друг на друга через TargetLinkedLogonId. Это объяснение опирается на документацию Chromium и не выводится напрямую из логов. Однако оно согласуется со всеми наблюдаемыми полями.

Это означает, что Windows создала два токена в рамках одной операции: один полный (Elevated: Да в 137224), другой ограниченный (Elevated: Нет в 137225). Именно так работает sandbox: полный токен нужен для настройки, ограниченный — для изолированной работы . При подборе пароля мы ожидали бы серию событий 4625 с одним TargetUserName перед успешным входом. В нашем логе 4625 только одно, и оно объясняется гонкой при инициализации, а не перебором.
